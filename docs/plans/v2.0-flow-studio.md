# v2.0 — Flow studio, part 1: flows as data

Status: proposal. v2 is split in three releases, each usable on its own:

- **v2.0 (this doc):** flows become data, with a simple list editor; custom agents with a role.
- **v2.1:** drag-and-drop editor on top of the same model.
- **v2.2:** parallel steps.

## Where we start

Today there is exactly one flow, Build & Review, and it is hardcoded everywhere:

- `packages/shared`: `AgentId = "forge" | "hawk"`, `FlowNode` is a fixed union of six nodes, `Task` has one `round`/`maxRounds`, one `verdict`, one `summary`.
- `apps/server/src/orchestrator.ts`: `loop()` runs `forgeStep → checksStep → hawkStep`; messages only target Forge (`forgeSteps`).
- `apps/server/src/app.ts`: `/api/agents/:id` only accepts `forge` and `hawk`. Providers branch on `role === "hawk"`.
- `apps/web`: `flow-graph.tsx` draws a fixed line of nodes; `run-model.ts`, `crew-view.tsx`, `glyph.tsx` and `/flows` (a static placeholder) assume the two agents.
- Demo mode rebuilds the flow as hardcoded steps (`lib/demo/demo-api.ts`, `scenarios.ts`).
- DB: JSON blobs per table, ad hoc migrations, no schema version.

## What v2.0 delivers

1. **Flows are data.** Build & Review becomes a built-in flow, and the engine runs any flow. Same behaviour as today for existing users.
2. **Your own flows**, made in a list editor on `/flows`: add, reorder and remove steps; set where a reviewer sends work back and how many rounds.
3. **Custom agents with a role.** Create agents besides Forge and Hawk, such as Scribe (writes docs) or Guard (security review), each one a **builder** (edits files) or a **reviewer** (read only).
4. **Pick a flow per task**, with a default per workspace.

### Steps available

| Step | What it does |
|---|---|
| Agent (builder) | Edits files in the worktree. Keeps its session across rounds; questions, decisions and mid-run messages work as in v1.9. |
| Agent (reviewer) | Reads the diff and returns a verdict. If changes are requested, the work goes back to the builder step it points to, up to N rounds. |
| Checks | Runs the repository's checks. A reviewer after it can't approve while a check fails (as today). |
| Ask me | Pauses and shows what was done so far. You continue, or send a message to the previous builder. |

The flow always ends with **You** (the merge decision). It isn't a step you add.

### Example flows

- **Build & Review** (built in): Forge → Checks → Hawk ↩ Forge (3 rounds).
- **Build, review, document:** Forge → Checks → Hawk ↩ Forge → Scribe → Ask me.
- **Two reviewers:** Forge → Checks → Hawk ↩ Forge → Guard ↩ Forge (2 rounds).

## Model

```ts
type AgentRole = "builder" | "reviewer";

interface Agent {
  id: string;            // "forge" and "hawk" stay as built-in ids
  name: string;
  role: AgentRole;       // new: was implied by the id
  provider: ProviderId;
  personality: Personality;
  instructions: string;
  builtIn?: boolean;
}

type FlowStep =
  | { id: string; type: "agent"; agentId: string; sendBackTo?: string; maxRounds?: number } // sendBackTo only for reviewers
  | { id: string; type: "checks" }
  | { id: string; type: "ask"; note?: string };

interface Flow {
  id: string;
  name: string;
  description: string;
  steps: FlowStep[];
  builtIn?: boolean;
}
```

- A task stores `flowId` and a **snapshot** of the flow, so editing a flow never breaks a running task.
- Per-step results: rounds per loop, and verdict, checks and summary keyed by step id. `Task.verdict`, `checks` and `summary` stay filled from the last step of each kind, so v1 screens keep working while they move over.
- The built-in flow uses the step ids `forge`, `checks` and `hawk`. Old tasks' `node` events then map onto it unchanged.
- Run events get a `stepId` where they relate to a step (`node`, `round`, `verdict`, `checks`, `handoff`). `FlowNode` widens to `string`.

## Engine

- `runFlow(task)` walks the snapshot step by step:
  - builder steps → today's `forgeStep`, generalized by agent;
  - reviewer steps → `hawkStep`;
  - checks → `checksStep`;
  - ask me → a new `waiting` reason.
- A reviewer that requests changes jumps back to its `sendBackTo` step and counts a round for that loop. When the limit is reached, the task goes to **You** (as today).
- Mid-run messages go to the active builder step, or to the last one when no builder is running. "Now" interrupts as in v1.9.
- Provider permissions come from the **role**, not the id: builders get `acceptEdits` and the workspace's command allowlist; reviewers get plan mode with Bash and edits disallowed (Claude) or a read-only sandbox (Codex).
- Prompts: `forge*` prompts become builder prompts and `hawkPrompt` becomes the reviewer prompt. The agent's name and instructions come from the agent.

## Storage

- New `flows` table (`id`, `data`, `created_at`), following the existing JSON-blob style.
- Agents: `agents` and `workspace_agents` accept any id. Custom agents live in the default crew or in a workspace's own crew, like overrides today.
- Workspace: `defaultFlowId`.
- Start versioned migrations with `PRAGMA user_version`, so this and later changes run once, in order.

## UI

- **`/flows`:** the list of flows (built-in ones are read-only but can be duplicated) and an editor that shows steps as a list. You can add a step (agent, checks or ask me), drag to reorder, and for reviewers pick "send back to" and the round limit. A live preview uses the graph.
- **Flow graph:** drawn from the flow snapshot instead of the fixed `ORDER`, still a straight line with loop arcs. It's the base for the v2.1 canvas.
- **Crew (`/crew`):** "New agent", with name, role, provider, personality and instructions. Built-in agents can't be deleted.
- **Top bar:** a flow picker next to the repository (defaults to the workspace's flow). Workspace settings: default flow.
- **Run screen:** filters and labels by agent instead of the fixed Forge and Hawk.
- **Demo:** `/flows` and Crew work in the demo (stored in the browser); simulated runs keep using the built-in flow.

## Out of scope for v2.0

- Drag-and-drop canvas (v2.1), parallel steps (v2.2).
- Conditions or branches other than "reviewer sends back".
- Different checks per step, and per-agent house rules.

## Work plan (one PR each)

1. **Engine on data, no visible change.** Shared model, `flows` table and migrations, the built-in flow, `runFlow` replacing `loop`, roles in providers. Done when a Build & Review task behaves exactly like 1.9.2 (real Claude Code run plus the mock crew).
2. **Custom agents.** `role` on agents, API without the forge/hawk restriction, Crew UI for creating agents, generic labels and glyphs.
3. **Flows.** Flows API, `/flows` list editor, flow picker on tasks and default flow per workspace, graph drawn from the snapshot, ask-me step.
4. **Demo, docs and release.** Demo support, README (How it works, Roadmap), CHANGELOG, v2.0.0.

## Risks

- **Regressions in the loop everyone uses.** PR 1 changes no behaviour and is tested against the same scenarios used for 1.9.1/1.9.2 (Now, next pause, review message, decide mode, questions).
- **Old data.** Tasks created before v2 have no flow snapshot. They're read as Build & Review.
- **Session reuse across several builders.** Each builder step keeps its own session id (`taskState.sessions[stepId]`).
